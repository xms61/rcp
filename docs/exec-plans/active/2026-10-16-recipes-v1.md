# Recipes v1: one recipe end to end

## Purpose
The owner can type in a recipe on the phone, find it again in the list, and cook from it: the four recipe pages, scaling, ticks, timers and the screen kept on. The recipe lives in SQLite on the server, and the recipes opened recently also work offline. This is the first slice of the designs in Penpot ([apps/mobile/DESIGN.md](../../../apps/mobile/DESIGN.md)).

**Left for later plans:**
- the food tables, linking foods and computed nutrition (the Nutrition page shows that nutrition comes with the food tables);
- import from a link, paste text and photos.

**How to see it working:** run the API locally, open the app in Expo Go, create a recipe in the editor, then open it and cook through it.

## Plan
1. **Schema.** zod schemas for a recipe and the list query in `packages/domain`, and the Drizzle tables with their first migration in `apps/api`. The API applies migrations when it starts, from `RCP_DB_PATH`. The image keeps better-sqlite3's prebuilt Alpine binaries, and compose mounts `./data` at `/data`. Check: domain and database tests; the bundle starts on an empty file and creates the tables.
2. **Recipe API.** Read and write functions in `apps/api/src/db/recipes.ts`, and the routes below, all validated with the domain schemas. Check: tests through `app.request` for each route, bad input, a missing recipe, every filter, and the token.
   - `GET /api/recipes` with search and filters;
   - `GET /api/recipes/:id`;
   - `POST /api/recipes`;
   - `PUT /api/recipes/:id`, which replaces the recipe with its lines and steps;
   - `DELETE /api/recipes/:id`.
3. **App foundation.** Check: unit tests for the theme, the API client and the cache.
   - Figtree;
   - light and dark theme tokens, with the accent as a token;
   - TanStack Query, with an API client that sends the token;
   - the router layout: home, recipe and editor;
   - the offline cache of recently opened recipes, with expo-file-system.
4. **Recipe list.** Search, the filter screen with include/exclude ingredients, the empty state and the offline banner. Check: component tests with a fake client.
5. **Recipe pages.** Check: tests for scaling, for amounts in steps, and for the keep-awake hook; the app shows a real recipe in Expo Go.
   - Overview, Ingredients, Steps and Nutrition, swiped or tapped;
   - servings scaling, and ticking lines and steps off;
   - amounts in brackets in the steps;
   - step timers;
   - the screen kept on in Steps.
6. **Editor.** Create, edit and delete a recipe, with its rating, flavor labels, groups, lines and steps. Check: component tests; create, edit and delete against the local API in Expo Go.

## Decision log
- 2026-10-16: The first build slice is one recipe end to end, typed in by hand. Rejected: the screens first on sample data, which means rework when the API lands; the food tables first, which leaves nothing to see for longer. The owner chose.
- 2026-10-16: The owner accepted ten recommendations in the start interview:
  1. Until the food tables exist, an ingredient line stores its amount, unit, food as text, note and original text. The link to a food comes later.
  2. No photo upload in v1. It needs `expo-image-picker` and a file store, so it comes with the import plan.
  3. Ratings, flavor labels and all three serving kinds are stored. v1 uses only "a share of the recipe".
  4. The database is one SQLite file at `/data/rcp.db`, the only writable path, bind-mounted from `/opt/rcp/data`.
  5. drizzle-kit generates SQL migrations, which are committed, and the API applies them at start.
  6. zod schemas live in `packages/domain`, used by both sides, with `@hono/zod-validator` in the API.
  7. The REST routes are the ones in milestone 2, and `PUT` replaces the whole recipe.
  8. TanStack Query fetches in the app, and recently opened recipes are saved as JSON with expo-file-system.
  9. Amounts in steps: the app finds each ingredient's name in the step text and adds the scaled amount in brackets.
  10. v1 filters on the food as written, plus taste, difficulty, price and time.
- 2026-10-16: The domain package's import rule allows `zod` and nothing else (`eslint.config.js`, tested in `scripts/lint-rules.test.mjs`), because both sides need the same validation. Zod does no I/O, so the domain stays pure.
- 2026-10-16: better-sqlite3 13, because it ships prebuilt binaries for every platform, Alpine included, and has no install script. The image copies the package without its C sources, and esbuild leaves it out of the bundle. Rejected: compiling in the image, which needs a toolchain and is slow under QEMU for arm64; Node's built-in `node:sqlite`, which is not stable in Node 24 and which the owner didn't choose.
- 2026-10-16: Ids are SQLite integers, since only the server creates recipes. Timestamps are ISO strings.

## Surprises
- 2026-10-16: drizzle-kit 0.31 pulls in esbuild 0.25 and 0.18 as dev dependencies, beside the API's own 0.28. They run only when drizzle-kit generates a migration on a development machine, and never go into the image.
- 2026-10-16: Penpot's plugin API names a shape "a / b" when given "a/b", and its flex children don't always lay out in array order after a clone. This was found while drawing; it only matters to agents editing the Penpot file.
